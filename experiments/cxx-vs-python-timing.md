# Field-scale timing: the C++ against the Python it replaced, 2026-07-26

> **Historical.** The Python half is the prototype, now frozen at
> `archive/python-prototype/`, so this comparison cannot be re-run as it
> stands. The speedups below stand; **one conclusion does not** -- see the
> note at "The LM is essentially all basis evaluation" further down.

A synthetic problem at validation scale -- 6561 columns, 100 probes, 100
fitted rows, `tau_window = 5`, levels [0,1,2], mu pinned, `n_rungs = 4`,
`window_shape_rungs` off. Seeded, self-contained, and using no private data
despite the scale it imitates.

Generated by `experiments/bench_field_scale.cpp`, which dumps the problem to
raw binary; the Python half loaded the same bytes. Built with
`-O3 -march=native`; a Debug build's timings would be meaningless.

## Head to head

Both ran the BALL window (`window_aspect_cap = 1`), which is what the prototype
derives, so the work is the same. Mean window 283 points either way; 100/100
rows shipped either way.

| | total | per row | vs prototype |
|---|---|---|---|
| Python prototype | 24.125 s | 241.3 ms | 1x |
| C++, 1 thread | 2.864 s | 28.6 ms | **8.4x** |
| C++, 2 threads | 1.494 s | 14.9 ms | 16.1x |
| C++, 4 threads | 0.955 s | 9.6 ms | **25.3x** |

The ellipsoid window (`cap = infinity`, the C++ default) is a further 1.6x on
top -- 1.783 s single-threaded, mean window 146 points instead of 283. That is
less work, not faster work, and it is the setting whose accuracy is unmeasured.

Threading scales 1.92x on 2 and 3.00x on 4.

## What that means for the replay

A whole-field fit is 6557 rows, not 100:

- prototype, single process: ~26 min
- C++, 4 threads: **~63 s**

So a `window_aspect_cap` sweep of five settings is about five minutes rather
than two hours.

## Where the time goes

One row (window 314 points, 17 candidates): 25.6 ms.

| component, at that size (6 modes) | time |
|---|---|
| `fit_varpro`, one candidate | 840 us |
| `linear_cv_score` | 219 us |
| `basis(theta).values()` | 13.0 us |
| `basis(theta).vjp(w)` | 25.5 us |

The accounting closes: 17 candidates x (840 + 219) us = 18.0 ms, plus the
baseline guard's three `linear_cv_score` calls (~0.7 ms), against 25.6 ms
measured -- the remainder being basis construction, admissibility and window
slicing.

So, top down:

1. **~70% of a row is the outer LM loop** (`fit_varpro`, one per candidate).
2. **~15% is cross-validation scoring** (`linear_cv_score`, one per candidate
   plus the baseline sets).
3. Within `fit_varpro`, one iteration costs `values()` + `vjp()` = 38.5 us, and
   at ~20 iterations that is ~770 us of the 840 us. ~~**The LM is essentially
   all basis evaluation.**~~

> **SUPERSEDED.** That conclusion held only because this run used SIX modes.
> At production mode counts the fit is **SVD-bound**, not basis-bound -- 61%
> of instructions at k = 100. Measured in `inner-solve-profile.md`, which is
> what motivated the QR-first inner solve. Do not cite the sentence above.

## One unmeasured optimization candidate

`linear_cv_score` at 219 us does five folds, each a `BDCSVD` solve of roughly
an (80, 7) matrix -- about 44 us for a very small least-squares problem. A
column-pivoted QR, or normal equations, would likely be much cheaper, and it is
called once per candidate plus once per baseline set.

NOT measured. The alternative has not been timed and the rank-revealing
behaviour of the SVD may be load-bearing for near-degenerate design matrices,
which is exactly the case the ridge and the rank cutoff exist for. Worth a
measurement before touching.
